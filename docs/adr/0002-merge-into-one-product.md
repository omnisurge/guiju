# ADR 0002 · 合并为一个产品：guiju 吸收 spec-currency

- 状态：**已采纳，分期实施中**（期 2 已完成；期 1 的 M1/M2/M3 已完成，下一步 M4；默认时效实现未切换）
- 决策人：所有者（2026-10-30："spec 是不是合并到一个产品内更好，而且地标规范应该支持查询和下载"）
- 取代：ADR 0001 第三节「合产品，不合代码仓」的结论、第五节「若必须统一语言应把 guiju 移植到 Go」的方向
- 影响：仓库形态、实现语言、合规边界、部署形态（合并后落到香港服务器）、`spec-currency` 的生命周期

## 进展（2026-10-31）

**"能下"这一半已先行落地（v0.10.0）**：新增 `guiju/sources/shzjw.py`，直接对接上海工程建设标准的
检索与下载 API，`guiju pull --source shzjw DG/TJ08-2007` 实测拿到 2,084,644 字节 PDF 并归档。

同时确认了一件对本 ADR 有利的事实：**spec-currency 已经在查询同一个上游**（它返回的记录里
`source` 就是 `shzjw`）。也就是说"地标从哪来"这件事，两边已经收敛到同一源，
合并时应当**归一化成一份实现**，而不是两套适配器并存 —— 这正是本 ADR 保留"合并"结论的技术依据。

- 注册表、保守 fallback、ccsn/std_samr/jtst/dbba 与八份原始 golden 均已落地；

### M3 源权威修正（2026-10-31，所有者裁定；随后已授权实施）

> “工标网一般没有地标信息，上海市地标就是从上海住建委获取即可，他就是唯一真相。”

此裁定取代此前 `DG/TJ = Composite(shzjw + csres)` 的方案，不以旧 Go 的既有实现作为继续双源设计的理由：

1. **上海地标以上海住建委 `shzjw` 为唯一真相**，不查 csres 做交叉校验，不以它或其他元数据源补判/覆盖上海源结论。
2. **M3 改为上海官方单源接入**：复用现有上海源的检索与解析，接到原生 `Currency` / 路由；
   根据官方已收录的上海编号范围做专门分流，优先于通用路由，不把该决定扩大到其他省市。
3. 状态按源站现行/废止分栏原样映射；未命中不猜，源失败不转外源。
   若用已验证的同源 TTL 缓存，仍须明确年龄和降级，不把旧缓存当作刚查的官方结论。
4. **不移植 Composite，不新增双源冲突模型，也不再写第二份地标解析器**。现有正文下载路径不变。
5. M3 验收改为官方记录/状态映射、无记录与失败语义、不得调用其他源、缓存来源隔离及离线回归；
   不再要求“两源状态一致”。该裁定最初只修正文档，随后所有者明确授权 M3，实施记录如下；默认/NAS/部署边界不变。

## 一、为什么改判（诚实记录）

ADR 0001 反对合仓的三条理由——部署生命周期不同、合规面必须分离、已验证资产不该重写——
在"只做目录 / 时效 / 引用串"这个范围里是成立的。两条新需求把平衡打破了：

1. **地标（`DG/TJ`）要能查、能下。**
   上海住建委的解析能力**已经存在**：`spec-currency/internal/adapter/shzjw.go`（279 行）。
   不合并，就得在 guiju 里再写一个同样的解析器 —— 同一站点两份实现，改版时各修各的。
2. **"精准下载"依赖权威状态。**
   v0.7.0 能修掉"拿错书"（`GB 50016-2014` → 《建筑防火通用规范》），靠的正是权威名称 +
   发布角色判定。这条链本该是一个产品内部的两步，拆成两个进程反而多了一个单点
   （NAS 不可达 → 退化为 31）。

不合并的代价，从此前的"语言不统一"变成了"长期双份维护 + 一个可靠性单点"。

## 二、决策

1. **一个仓、一个产品**：`guiju`（Python，零运行时依赖）存活；`spec-currency`（Go）冻结归档。
2. **移植方向：小的搬进大的。**
   把 spec-currency 的适配器（`csres` / `shzjw` / `jtst` / `ccsn` / `dbba` / `stdsamr`
   + `httpx` / `registry` / `fallback`）与缓存、查询、TSV 契约移植进 guiju 的 `Currency` 端口之后。
   旧 `composite` 不移植（见 2026-10-31 的 M3 源权威修正）。
   **不**反向重写 guiju —— 它的领域知识（发布角色、可得性分档、歧义策略、合规闸）是
   八轮实测踩出来的，重写等于重踩一遍。
3. **两个入口，一个代码库**：
   ```
   guiju <命令>     # 本地 CLI（一期已有）
   guiju mcp        # 服务面：kb-system / jl-docx 的时效查询，契约逐字保持
   ```
4. **部署形态（所有者 2026-10-31 决定）**：两仓合并完成后**一次性部署到香港服务器**
   （`hk`，38.76.165.16），用于**外网使用**；不再部署到 NAS。
   - 本机**不**再单独安装 `spec-currency`（不装 PATH、不做本地常驻）；
   - NAS 上的 `:18083` 维持现状到合并完成，之后由合并后的服务取代；
   - 注意 NAS 有 ADR0048 的**变更冻结**（缺陷清单清零前不对其执行部署步骤）——
     这是运维约束，不是 NAS 故障。
5. **合规边界从"进程边界"降为"代码边界"**，并加硬约束与测试断言：
   - 只有 `compliance.py` 能取正文；
   - 正文主机只能是 `*.gov.cn`（`zjw.sh.gov.cn` 属此列，地标正文因此合法）；
   - 元数据适配器**禁止**调用 `compliance.get`、禁止落文件（用测试钉住，不靠约定）。

## 三、分期与验收（每期独立可验收）

| 期 | 内容 | 验收标准（不靠"看起来对"） |
|---|---|---|
| 1 | 适配器 + 缓存 + TSV 契约移植，`Currency` 端口换实现 | 用 spec-currency 自带 golden `testdata` 做**离线回归**；同一批编号与 NAS 版**逐字段 diff**（status / name / implement_date）必须一致 |
| 2 | `shzjw` 接成**内容源**：`DG/TJ` 从 31 变为可下载 | 取 2–3 本上海地标正文 + 出引用串 + `verify` 通过 |
| 3 | `guiju mcp` 服务面 | TSV / JSON-RPC 契约逐字不变；kb-system 的 code_refs 校验结果一致 |
| 4 | 归档 spec-currency（只读），文档写清单一形态 | 消费者全部切到 guiju 后，Go 服务停止 |

**第 1 期是唯一的高风险期**：移植必然产生解析偏差。能不能安全落地，全看有没有把
spec-currency 的 golden testdata 当金标准做 diff —— 这是本 ADR 的硬前置条件。

## 四、风险与缓解

| 风险 | 缓解 |
|---|---|
| 移植解析偏差（最可能） | golden testdata 离线回归 + 线上逐字段 diff；不一致即阻断，不带病合并 |
| 合规红线被稀释 | 正文出口唯一化 + `*.gov.cn` 断言 + 元数据适配器禁用 `compliance.get`（测试级） |
| 一期能力回退 | `scripts/e2e.py`（36 项）+ 单测作为回归门，每期合并前必跑 |
| 消费者中断（kb-system / jl-docx） | 第 3 期并行运行一段，逐字段 diff 确认结果一致后，再切换消费者；切换由所有者决定 |
| NAS 变更冻结（ADR0048）与部署冲突 | 合并后的服务**只部署到香港服务器**，不依赖 NAS 侧变更，冻结不影响本 ADR 推进 |
| 服务面契约漂移 | 两侧契约测试互钉（`test_currency.py` + kb-system 的 `verify` 契约） |
| 二期范围膨胀 | 只做上述四期；不顺带加新功能（不做缓存分层、不做并发、不做 UI） |

## 五、明确不做

- 不做第二种实现语言（不双语言、不 cgo）。
- 不在二期开始前合并代码仓——一期以 ADR 0001 形态收尾即可交付。
- 不把 `spec-currency` 的 `feedback` / `batch` 盘点形态整套搬进来：`batch` 的状态盘点
  在合并后由 `guiju` 的 mcp 侧承载，形态到时再定，不预设。
