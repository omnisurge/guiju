## 一、先回答两个问题

### 1. 可行吗？—— 可行，而且技术上比想象的简单

我今天已经用不到 1 小时跑通了全链路：**42 本 / 316MB，全部来自 `.gov.cn`**，成功率从 65% 修到 100%。
技术上真正难的不是"抓"，而是**"认得出哪个附件才是规范"**和**"站点改版后快速修"**。这两点决定了工具是玩具还是能长期用的基建。

### 2. 违法吗？—— 不违法，但有四条明确红线

这一节我不给模糊结论，直接判定。

| 行为 | 判定 | 依据 |
|---|---|---|
| 下载**强制性标准**（GB 55xxx） | ✅ 完全合法 | 《标准化法》第 17 条：强制性标准文本**应当免费向社会公开**。这是法定义务，不是你薅羊毛 |
| 下载**推荐性标准**（GB/T、JGJ、CJJ/T）政府已公开全文 | ✅ 合法 | 同条：国家**推动**免费公开推荐性标准。发布机关主动公开，你获取公开内容不构成侵权 |
| 个人/团队**内部查阅、检索、辅助设计** | ✅ 合法 | 合理使用范畴 |
| CLI 作为**开源工具**分发（不含标准文件本体） | ✅ 合法 | 分发的是"抓取方法"，不是受版权保护的作品 |
| 工具**内置标准库对外提供下载服务**、打包转售 | ❌ 高风险 | 实质是二次发行，出版社的出版权仍在 |
| **绕过**验证码 / 登录 / 付费墙 / WAF | ❌ 可能违法 | 可能触及《刑法》285 条"非法获取计算机信息系统数据" |
| **高频请求**打瘫站点 | ❌ 违法 | 《网络安全法》第 27 条：不得干扰网络正常功能 |
| 抓**非公开**内容（内部库、付费电子书库） | ❌ 违法 | 同上 |

**一句话结论**：抓政府已公开的正文 → 合法；破解付费墙或再分发售卖 → 违法。中间那条线很好守。

> ⚠️ 我不是律师，以上是基于条文的工程判断。真要商业化（收费提供标准服务），务必找专业律师过一遍。

## 二、边界设计：把合规写进架构，而不是写进 README

这是我最想强调的一点。合规不该靠"开发者自觉"，应该靠**代码默认拒绝**。

```
┌─────────────────────────────────────────────────┐
│  ComplianceGuard（所有出站请求的必经关卡）        │
│                                                 │
│  1. 域名白名单：仅 *.gov.cn + 已审核姊妹域       │
│     → 非白名单直接抛错，不给 override 开关        │
│  2. robots.txt 解析 + 缓存，Disallow 即拒         │
│  3. 令牌桶限速：默认 1 req / 2s / host           │
│     支持 Retry-After，绝不重试风暴                │
│  4. 反爬特征检测：遇到验证码/401/JS挑战 → 直接放弃 │
│     （不做任何绕过尝试，记录为 UNSUPPORTED）      │
│  5. UA 诚实标识：GJStd/0.1 (+联系邮箱)           │
│     不伪装成 Chrome 去骗过 WAF                    │
└─────────────────────────────────────────────────┘
```

**关于第 5 点我要提醒你**：我今天为了跑通用了伪装 UA，这是**临时手段，不该固化进产品**。诚实的 UA + 合理频率，对政府站点的公开内容是够的；如果被拦，说明该源不该抓，放弃它比绕过它正确。

## 三、系统架构

```
                        ┌──────────────┐
                        │   CLI 入口    │  gjstd search / get / sync / verify
                        └──────┬───────┘
                               │ JSON 优先（agent 友好）
                        ┌──────▼───────┐
                        │   Resolver    │  编号/名称 → 标准实体 + 源页面
                        │  模糊匹配     │  处理"GB 50352-2019" / "民用建筑统一标准"
                        └──────┬───────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
      ┌───────▼──────┐ ┌───────▼──────┐ ┌──────▼───────┐
      │ SourceAdapter │ │SourceAdapter │ │SourceAdapter │   ← 每源一个适配器
      │   mohurd      │ │  sh_zjw       │ │  sc_119      │     彼此隔离，坏了不影响
      └───────┬──────┘ └───────┬──────┘ └──────┬───────┘
              └────────────────┼────────────────┘
                               │
                    ┌──────────▼───────────┐
                    │  ComplianceGuard      │  ← 所有请求必经
                    └──────────┬───────────┘
                               │
                    ┌──────────▼───────────┐
                    │  Downloader           │  断点续传 / 重试退避 / 流式落盘
                    └──────────┬───────────┘
                               │
                    ┌──────────▼───────────┐
                    │  Verifier             │  魔数 / 页数 / 文本采样 / sha256
                    └──────────┬───────────┘
                               │
              ┌────────────────┴────────────────┐
              │                                 │
      ┌───────▼────────┐              ┌─────────▼─────────┐
      │  Catalog (SQLite)│              │  文件仓库          │
      │  元数据 + 状态   │              │  {code}/{sha}.pdf  │
      └────────────────┘              └───────────────────┘
```

### 设计取舍三条

1. **源优先，不用搜索引擎**。搜索引擎结果页掺水（我今天就遇到过建标库的证书警告页面）。权威源直连，准确率有保障。
2. **适配器必须可单独替换**。住建部半年内就把 `zhengcefilelib/...` 全量迁移到 `art_17339_...`，硬编码必死。
3. **文件按内容寻址**（sha256 命名 + 元数据指向），避免重复下载，天然支持去重与校验。

## 四、数据模型

```sql
-- 标准实体（一个编号一个版本一行）
CREATE TABLE standards (
  id            INTEGER PRIMARY KEY,
  code          TEXT NOT NULL,          -- 归一化后：GB55037-2022（无空格）
  code_raw      TEXT,                   -- 原始："GB 55037-2022" / "GB55037-2022"
  name          TEXT NOT NULL,          -- 建筑防火通用规范
  level         TEXT NOT NULL,          -- 国家强制/国家推荐/行业/地方/团体
  mandatory     INTEGER DEFAULT 0,      -- 是否全文强制（决定合规等级）
  issuer        TEXT,                   -- 住房和城乡建设部
  publish_date  TEXT,
  effect_date   TEXT,
  status        TEXT DEFAULT 'unknown', -- 现行 / 废止 / 即将实施
  replaced_by   TEXT,                   -- 被替代
  UNIQUE(code)
);

-- 来源与文件（一个标准可能多源，主源 + 备源）
CREATE TABLE artifacts (
  id          INTEGER PRIMARY KEY,
  std_id      INTEGER REFERENCES standards(id),
  source_id   TEXT,        -- mohurd / sh_zjw / sc_119
  source_url  TEXT NOT NULL,   -- 公告页（人类可复核）
  file_url    TEXT,            -- 附件直链（易失效，仅缓存不互通）
  sha256      TEXT UNIQUE,
  bytes       INTEGER,
  pages       INTEGER,
  fetched_at  TEXT,
  verify      TEXT         -- ok / not_pdf / wrong_attachment / truncated
);

-- 抓取韧性：每个源的失败模式要能统计出来
CREATE TABLE fetch_log (
  id, source_id, target, http_code, result, note, ts
);
```

`verify` 字段是我今天最痛的一课：13 个文件"下载成功"但其实是 `.doc` 废止条文或 20KB 错误页。**必须落库，不能只看 HTTP 200。**

### 住建部适配器：核心逻辑（已跑通的真实实现）

```python
# 1) 旧链接 → 新详情页（旧格式已 100% 失效）
def to_detail(old_url):
    m = re.search(r'/zhengcefilelib/(\d{4})(\d{2})/\d{8}_(\d+)\.html', old_url)
    if m:
        y, _, pid = m.groups()
        return f'https://www.mohurd.gov.cn/gongkai/zc/wjk/art/{y}/art_17339_{pid}.html'
    return old_url

# 2) 附件不能只取第一个！第一个常是「废止的强制性条文」(.doc)
BAD = ('废止', '条文', '说明', '公告', '通知')
def pick_attachment(atts, std_name):
    cand = [a for a in atts if not any(b in a.label for b in BAD)]
    key = re.sub(r'[《》\s]', '', std_name)
    for a in cand:                       # 按名称匹配
        if key in re.sub(r'\s', '', a.label):
            return a
    return cand[0] if cand else None
```

### 三个已踩过的坑（写进文档，避免二次踩）

| 坑 | 现象 | 对策 |
|---|---|---|
| 旧 URL 全失效 | `zhengcefilelib/…` 返回 404/空 | 映射到 `art_17339_*` 新格式 |
| 附件选错 | 拿到 15~30KB 的 `.doc`（`D0CF11E0` 魔数） | 按名称匹配 + 魔数校验 |
| 下载子域报废 | `download.mohurd.gov.cn` 一直 504 | 只用 `www.mohurd.gov.cn` 的 JPAAS 网关 |
| 中文文件名 | `UnicodeEncodeError` | `fileName=` 参数必须 percent-encode |
| 缺 Referer 被拒 | 403 | 带公告页 Referer |

### 发现层（Discovery）：不依赖预先知道书名 —— 已打通

这是决定 CLI 是"查书工具"还是"标准索引"的分水岭。实测结论：**住建部有可枚举的完整目录，不需要任何人先报书名。**

**接口**（`标准公告` 栏目的列表构建接口，GET）：

```
GET /api-gateway/jpaas-publish-server/front/page/build/unit
  ?parseType=bulidstatic
  &webId=86ca573ec4df405db627fdc2493677f3
  &tplSetId=fc259c381af3496d85e61997ea7771cb
  &pageType=column
  &tagId=栏目-list
  &editType=null
  &pageId=Y53uSscFTKvrbHxaF9Cvp
  &paramJson={"pageNo":1,"pageSize":20}     ← 关键：嵌套 JSON 字符串
```

三个坑：
1. `pageNo` **不能**作为顶层参数，必须塞进 `paramJson` 的 JSON 字符串里，否则永远返回第 1 页
2. 响应是 `{"data":{"html": "<li>...</li>"}}`，要二次正则解析 HTML
3. 分页元数据也在 HTML 里：`<div class="pagination" rows="20" count="3254" pageNo="1">`

**实测结果**（2026-10-30）：

| 指标 | 数值 |
|---|---|
| 公告总数 | **3254 条** |
| 时间跨度 | 2000-02-11 ~ 2026-09-23 |
| 分页 | 163 页 × 20 条，约 3.5 分钟跑完 |
| "发布国家标准" | 1487 条 |
| "发布行业标准" | 778 条 |
| 局部修订 | 86 条 |
| 建筑/土木相关（关键词命中） | 1395 条 |

**架构含义**：CLI 的 `search` 不该去搜索引擎捞，应该**本地缓存这份 3254 条目录**，检索走 SQLite。增量同步每天只需扫 `pageNo=1`，遇到已见日期即停，1~2 次请求。

**唯一需要进详情页的**：目录标题里有「标准名称 + 日期 + 链接」，但没有**标准编号**（GB/JGJ 号在正文里）。所以 `sync` 是两段式：目录枚举 → 对新增条目抓详情页解析编号。这仍是数据驱动，不靠世界知识。

**编号格式在 2026 年变了**：早期是 `art_17339_{数字自增}`（数字连续，可区间探测），2026 年起改为 `art_{32位hex}`（不可枚举）。所以**目录接口是唯一可靠的发现入口**，不要指望 ID 遍历。

## 六、CLI 接口设计（agent 优先）

设计原则：**默认 JSON、可幂等、退出码语义化、不交互**。Agent 最怕"卡在交互提示"和"输出人类日志"。

子命令按**监理的实际动作**排，不按程序员习惯排：

```bash
# 1) 检索：走本地 SQLite，不联网，秒回
guiju search "建筑防火"
guiju search 防火 --level 强制 --status 现行 --json
# → [{"code":"GB55037-2022","name":"建筑防火通用规范","mandatory":true,
#     "source":"mohurd","url":"https://www.mohurd.gov.cn/..."}]

# 2) 看详情：编号 / 名称 / 状态 / 公告页 / 本地是否已有
guiju show GB55037

# 3) 下载：幂等，已存在且校验通过则直接返回路径（退出码 10）
guiju pull GB55037 --out ./规范/ --json
# → {"code":"GB55037-2022","path":"./规范/GB55037-2022_建筑防火通用规范.pdf",
#    "sha256":"...","bytes":66260920,"verified":true}

# 4) 出引用串：监理通知单 / 旁站记录直接粘贴
guiju cite GB55037 5.2.1
# → 《建筑防火通用规范》GB 55037-2022 第 5.2.1 条
guiju cite GB55037 5.2.1 --json
# → {"cite":"《建筑防火通用规范》GB 55037-2022 第 5.2.1 条",
#    "code":"GB55037-2022","clause":"5.2.1","url":"https://..."}

# 5) 同步目录：增量，遇到见过的日期即停（每天 1~2 次请求）
guiju sync --json

# 6) 校验本地库：是否缺文件 / 被替换 / 版本过期
guiju verify --all --json

# 7) 溯源：任何文件都能反查"哪来的、什么时候、哪一页附件"
guiju provenance ./规范/GB55037-2022_建筑防火通用规范.pdf
```

> `cite` 是这个工具在监理场景里的**真正价值点**。出通知单必须写"依据《XX》第X条"，以前靠翻 PDF 手抄，现在一条命令出标准引用串——比"能下载"值钱得多。

**版本串带台账信息**，便于事后说清"我查的是哪一天的目录"：

```
$ guiju --version
guiju 0.1.0 · catalog 2026-10-30 · 3254 records
```

**退出码约定**（让 agent 能自己决策）：

| 码 | 含义 | Agent 该怎么做 |
|---|---|---|
| 0 | 成功 | 继续 |
| 10 | 已存在且校验通过 | 跳过，别重复下 |
| 20 | 源不可达（网络/504） | 稍后重试 |
| 30 | 附件不存在或格式不符 | 换备源，或报人工 |
| 40 | 命中合规护栏被拒 | **停止，不要重试** |
| 50 | 需要人工介入（页面结构变了） | 上报 |

**关键**：`--json` 模式下 stdout 只输出 JSON，日志一律走 stderr。这样 agent 可以直接 `jq` 管道，不用解析人类文本。

## 八、明确不做的事（写进 LICENSE 和 README）

这些不是技术限制，是产品定位：

1. ❌ 不做标准文件的**公开下载站/网盘分发** — 这是侵权的核心红线
2. ❌ 不抓**团体标准**（T/CECS 等）— 无官方渠道，只能买
3. ❌ 不抓**标准图集**（G101 系列）— 不在公告体系内
4. ❌ 不绕过任何**验证码、登录、付费墙**
5. ❌ 不提供"一键打包 2000 本"的镜像能力 — 高频即违法
6. ❌ 不承诺**条文准确性** — 工具只保证"文件与官方发布版一致（sha256）"，条文解释以正式出版物为准

第 6 点尤其重要：**说明书里必须写清"本工具不生产内容，只做搬运与校验"**，责任边界才清晰。

## 九、一句话结论

**想法可行，法律上站得住，技术上已经验证过可行性。** 真正的护城河不是"能抓"，而是：

> 把「哪个附件才是规范」和「站点改版后 24 小时修好」这两件脏活工程化。

这两点做到了，它就是个能活三年的内部基建；做不到，就是个跑两周就烂的脚本。
