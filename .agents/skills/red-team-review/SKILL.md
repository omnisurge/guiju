# 红队代码审查（Red-Team Review）

> 定位：只找**真实、可达、可证伪的缺陷**；宁可放过主观改进意见，绝不制造一条没有触发路径的噪音建议。

## 一、铁律（必须严格遵守）

1. **必须精确举证**：你指出的**每一条**缺陷，必须同时满足以下两项：
   - 给出**精确的文件路径与代码行号**（如 `path/to/file.py:123`）；
   - 给出**能实际触发该缺陷的具体输入参数、状态前置条件或完整执行路径**（尽量附最小复现命令或断言）。
2. **无法举证即「通过」**：如果你找不到同时满足以上两项的真实缺陷，**必须直接输出 `通过`**，不得退而求其次改提“建议关注”或“可能存在风险”。
3. **绝对禁止项（零容忍）**：
   - 绝对禁止提出代码风格、排版缩进、变量或文件命名规范问题；
   - 绝对禁止提出注释措辞、抽象拆分偏好等审美性建议；
   - 绝对禁止提出缺乏真实可达触发路径的主观“防御性编程”建议（如“建议这里判空以防万一”）。

## 二、两种执行模式

### 1. 发版前 / 核心改动全量审查

适用于功能迭代收口、跨模块契约变更或发版冻结前：
1. 列出待审改动面：`git status` 与 `git diff <base>..HEAD`（或工作区未提交差异）。
2. 沿修改点**向外追查粘连面**：上下游调用方、CLI/API/MCP 入口、持久化与序列化边界、错误码与降级分支、并发锁与缓存读写，禁止只看被改动的几行本身。
3. 重点核查四类高发真实缺陷：
   - **边界与畸形输入**：正则回溯（ReDoS）、零值/空值/`limit=0`、全半角与特殊字符、非法编码或超限载荷；
   - **契约与状态不一致**：非预期退出码/错误原因、伪成功、`--offline`/禁用态/截断空结果被当成权威“无记录”、只看展示列表而非总数；
   - **时间与生命周期**：未来时间戳/时钟漂移、`clock` 注入未透传、锁粒度过宽或跨线程共享可变状态、资源句柄泄漏；
   - **错配与边界绕过**：分类器漏判后回落到同名错误实体、校验被外层捷径绕过、只读命令意外建目录或写盘。
4. 尽量对怀疑点用只读复现脚本或单测验证触发后再写入结论。

### 2. 修复后轻量复查（Re-review）

适用于修复红队问题或评审意见后、合入/发版前的收敛检查：
1. 聚焦修复引入的 `diff` 与新增/修改的正则、条件分支及调用粘连面，不必从头重复全仓审计。
2. 重点追查两件事：原漏洞的所有入口是否都已封死（含绕过路径与兜底路径）、修复代码本身是否新引入回归（如 ReDoS、边界误伤或新状态不一致）。
3. 跑完相关单元测试与项目门禁；未发现新的可举证缺陷时，直接输出 `通过`。

## 三、输出格式

- **发现真实缺陷时**，按影响严重度从高到低逐条输出，每条只含以下 4 项：
  1. **位置**：`精确文件路径:精确行号`（可附对应符号名）
  2. **触发路径 / 输入**：具体参数、状态前置条件或调用链路（如可复现则给出最短命令或输入样例）
  3. **实际后果**：会发生什么错误行为（越界、错配、假阳性/假阴性、崩溃、耗时爆炸等）
  4. **最小修复方向**：直指根因的改动范围
- **未发现真实可举证缺陷时**：只输出 `通过`（可附一行已核验的提交范围或基线命令）。
